# 复盘总结

## 1. 项目回顾

这个项目从“素材审核与发布排期”的业务场景出发，最终交付了一条可运行、可观察、可复现的 ReAct 链路：

```text
用户自然语言请求
  → ReActAgent
  → DeepSeek 选择工具
  → 读取素材 / 审核规则 / 查询时段 / 保存草稿
  → observation 回填
  → 继续决策
  → 最终回答
```

项目没有把业务决策写死成固定脚本。模型在真实 API 运行中自行选择工具；工具只返回素材、规则、时段和保存结果。六条评估路径覆盖了正常排期、信息不足、规则风险、时段冲突、重复提交和保存失败。

## 2. 亮点

### 2.1 真实 ReAct 链路跑通

`examples/case_normal.md` 记录了一次完整的四步链：

```text
read_material → check_rules → query_slots → save_draft
```

模型不是按代码里的固定顺序执行，而是读取每一步 observation 后决定下一步。保存成功后，模型在最终回答中返回 `draft_id`，并明确“仅保存草稿，未真实发布”。

### 2.2 冲突场景不越权

`case_conflict.md` 中，模型发现 18:00-18:30 已被占用，给出了 18:30-19:00 的替代时段，并请求用户确认。它没有因为“用户说 18:00”就自行改到 18:30 保存，体现了“硬性发布时间未经确认不改”的边界。

### 2.3 重复提交幂等

`case_duplicate.md` 连续执行两次提交。第一次保存返回 `duplicate=false` 和新 `draft_id`；第二次返回 `duplicate=true`，并沿用同一个 `draft_id`。两次运行后草稿仍然只有 1 条。这说明幂等由存储层保证，而不是依赖模型“记得不要重复”。

### 2.4 失败如实上报

`case_save_fail.md` 中，M04 的保存连续两次失败，模型明确告诉用户“草稿未能保存”，没有返回成功状态，也没有虚构 `draft_id`。保存失败时如实上报，是比“看起来成功”更重要的业务底线。

### 2.5 证据链完整

每个 case 都保留了：

- 用户输入；
- 逐步工具 trace；
- 模型最终回答；
- 草稿数量和导出状态；
- 对照需求的验收判定。

这使评审可以检查“模型到底做了什么”，而不是只看一段最终文案。

### 2.6 工具与决策解耦

`tools.py` 没有“遇到 M03 就拒绝”“看到 M01 就保存”的分支。M03 的风险来自 `rules.json`，重复保存的幂等来自唯一键，冲突替代时段来自 `schedule.json`。模型负责解释和选择，工具负责返回事实。

## 3. 风险与不足

### 3.1 规则引擎仍是简化版

当前规则只覆盖关键词绝对化用语和医疗健康分类，规则维度、严重级别、权重、版本管理和可解释性都不足。真实内容审核通常还涉及图片、视频、上下文语义、品牌规范、广告法和平台政策，这些都没有覆盖。

### 3.2 时段粒度固定为 30 分钟

`query_slots` 只处理 30 分钟对齐的 `HH:MM` 时段，没有日期、时区、跨天、周期性排期和不同渠道独立日历。真实排期系统通常需要按日期、渠道和发布队列建模。

### 3.3 草稿存储是本地 JSON

`data/drafts.json` 是演示用的本地文件，没有并发锁、事务、多用户隔离、权限控制和审计日志。并发提交时，唯一键判断和写入之间存在竞态窗口；生产环境需要数据库唯一约束或分布式锁。

### 3.4 MockLLM 不能证明真实决策

MockLLM 只能验证循环、工具契约和关键路径的可回归性。它不评估模型是否理解“信息不足”“硬性要求”和“用户确认”的语义。真实效果必须看 `examples/` 的真实 API trace，而单次 trace 也不是统计意义上的稳定性证明。

### 3.5 真实模型存在随机性

同一输入重新运行，模型可能给出不同措辞，偶尔也可能跳过某个工具或直接请求确认。`case_normal` 首轮就因为输入不够明确而先请求确认，后来通过明确确认时段的输入重跑。这说明提示词和用户表达的清晰度会显著影响路径。

### 3.6 真实 API 的工程韧性不足

`DeepSeekLLM` 目前没有显式的超时、重试、退避、限流和熔断策略；网络异常或 API 限流时，CLI 可能直接失败。真实生产需要把这些能力放在模型调用层，而不是依赖 Agent 循环兜底。

### 3.7 评估规模仍然有限

最终 case 每个场景保留一次最终运行（duplicate 为两次提交），normal 和 save_fail 各因措辞或评估器问题重跑过一次。这足以证明链路可运行，但不足以证明模型在大量素材、长上下文、并发和边界输入下的稳定性。

### 3.8 确认机制仍依赖模型

当前“用户确认后保存”主要由系统提示、工具描述和受控场景约束，`save_draft` 没有独立的确认令牌，无法在服务端证明调用前一定发生过用户确认。生产环境需要把确认结构化，而不是只依赖模型自觉。

## 4. 改进方向

### 4.1 规则引擎化

- 将规则从简单关键词升级为可配置规则引擎；
- 支持规则版本、优先级、权重、适用渠道和生效时间；
- 为每条规则保留可解释的命中证据；
- 增加规则回归集，避免规则变更导致误杀或漏放。

### 4.2 更细粒度的时间模型

- 引入日期、时区和渠道日历；
- 支持 15 分钟、小时级等更细粒度；
- 支持跨天、周期性、黑名单时段和节假日；
- 在冲突检测中返回更完整的占用对象和冲突原因。

### 4.3 对接真实发布/排期系统

- 将 `save_draft` 替换为带权限和审计的草稿服务；
- 增加草稿版本、提交人、确认记录和发布前审批；
- 明确“草稿、待审核、已排期、已发布”的状态机；
- 保持“未经确认不真实发布”的硬边界。

### 4.4 增强模型调用的工程能力

- 为 DeepSeek 调用增加超时、重试、指数退避和限流；
- 增加错误分类，区分网络错误、鉴权错误、限流和模型输出异常；
- 在 trace 中记录耗时、token 使用和错误码；
- 对 `max_steps`、单次运行时长和成本设置预算。

### 4.5 提升并发与一致性

- 用数据库唯一约束保证 `material_id + slot` 的幂等；
- 为草稿写入加事务或分布式锁；
- 对并发提交做冲突检测，避免“先查后写”的竞态；
- 增加幂等键和重试安全说明。

### 4.6 扩大评估覆盖

- 每个场景重复运行多次，统计工具序列和结果的稳定性；
- 增加“用户拒绝替代方案”“用户确认替代时段”“规则 confirm-only”等独立 case；
- 引入人工评审，对最终回答的准确性、完整性和语气打分；
- 将真实 API 评估与 MockLLM 回归测试分层，分别作为质量门禁。

### 4.7 结构化用户确认

- 让 `save_draft` 接收 `approval_id` 或确认记录，而不是只依赖模型自述；
- 服务端校验确认对象必须是当前素材 + 当前最终时段；
- 记录确认人、确认时间和有效期，时段变化后旧确认自动失效；
- 把确认、草稿、审核和发布串成可审计的状态机。

## 5. 个人收获

这个项目最大的收获不是“让模型调用几个函数”，而是理解了 Agent 工程中几个容易被忽略的边界：

- **工具返回事实，模型负责决策。** 一旦把业务分支写进工具，所谓 Agent 就退化成固定脚本。
- **确认边界不能只靠提示词。** 当前原型主要靠系统提示、工具描述和受控场景保证；生产环境应让保存动作在结构上依赖可校验的确认记录。
- **失败路径比成功路径更能体现质量。** 保存失败、信息不足、规则拦截时是否如实上报，决定了系统是否可信。
- **评估器也需要被评估。** `save_fail` 的误判说明：自动判定可能把“没有保存成功”看成“保存成功”，证据质量需要反复校验。
- **真实 trace 比漂亮总结更有说服力。** 保留工具名、参数、observation 和最终回答，才能让评审判断模型是否真的在决策。

## 6. 结论

当前版本已经完成了一个可运行、可观察、可回归的最小闭环：

- 真实 DeepSeek ReAct 链路可跑通；
- 六条核心业务路径有真实运行证据；
- 冲突不越权、重复提交幂等、失败如实上报；
- 9 条自动化测试覆盖骨架和场景回归。

它还不是生产系统。规则、时间模型、存储一致性、发布系统对接和 API 工程韧性都需要继续补齐。但作为“素材审核与发布排期 Agent”的考核原型，它已经把最重要的决策链和边界验证清楚了。
